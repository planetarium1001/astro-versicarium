# 主题更新

## 范围

本篇覆盖：把主题新版本同步到站点、站点自有文件的保护、冲突处理。前置：站点已是自己的仓库并提交过，见[安装与运行](install.md)。

## 更新方向

- 单向：主题仓库 → 你的站点，站点不反向合并。
- 主题已脱离最初的派生关系，没有可跟踪的上游；更新只取主题仓库。
- 命令按文件合并，成功后更新 `theme.json` 里记录的主题提交。

## 更新范围

- 更新只涉及主题代码与主题资源，不涉及内容、设置与图片。
- 站点自有路径里的文件保持原样，报告里列为已跳过。
- 主题新增的默认设置不会覆盖你的设置文件。
- 主题新增的页面与组件会随更新写入；自己新增的文件不受影响。

## 站点自有路径

下面这些是站点自己的文件，主题更新只把它们列进报告，不修改：

- 内容：`content/`
- 设置：`src/data/settings/` 下的五个设置文件
- 图片与头像：`public/images/`、`public/author/`
- 字体：`public/fonts/`
- 工具清单与生成记录：`tools/`
- 测试快照：`tests/fixtures/`
- `README.md`
- 主题基准文件：`theme.json`
- 示例站发布配置：`.github/workflows/pages.yml`

想长期保留的定制，放进这些位置或单独的文件。

## 更新前确认

- 用 git 提交或暂存当前改动；工作区不干净时命令直接拒绝执行。
- 确认能访问主题仓库，命令会拉取它的最新提交。
- 记下自己改过的主题文件，冲突时优先保留自己的改动。
- 先了解主题这一版改了什么，确认影响范围。

## 执行步骤

- 先看会改什么：`npm run theme:update -- --check`。只列清单，不写文件。
- 执行合并：`npm run theme:update`。拉取主题最新提交，按文件合并。
- 处理冲突，再跑一次命令。
- 检查站点：`npm run verify`。

- 合并是逐个文件做的，每个文件归入一类。
- 中途失败时 `theme.json` 不更新，修正后可以重跑。
- 没有新内容时提示已是最新，什么也不做。
- 命令需要 git 与网络，第一次运行会拉取主题仓库。
- 合并完成后，报告会分成已更新、已合并、已跳过、存在冲突、主题已删除几类。
- 已跳过的文件就是站点自有路径，报告里能看到完整清单。

## 冲突处理

- 冲突标记写进对应文件，命令以失败状态结束，`theme.json` 保持原样。
- 手工解决标记后重跑命令；重跑前可以先再跑一次 `--check` 看剩余改动。
- 二进制文件冲突时保留站点版本，按报告核对是否需要主题的新文件。
- 报告里「主题已删除」的文件不会自动删除，确认没用之后自己删。
- 站点自有路径不会进入合并，冲突只可能出现在主题负责的文件里。
- 同一个文件反复冲突时，把自己的改动挪到单独文件或站点自有路径，减少下次冲突。

## 更新后确认

- `npm run verify` 通过，页面记录有变化时一起提交。
- 打开首页与文章页，确认样式、图片、字体正常。
- 抽查一处自己改过的主题文件，确认定制还在。
- 更新不需要改设置文件，也不需要重新写内容。
