主题更新把主题仓库的新版本合并到站点，只改页面、组件、样式、脚本与默认配置。站点自己的内容、设置、图片、头像与字体保持不动。

只改内容时不需要执行主题更新，主题仓库有新提交或新版本时再同步。

## 更新方向

- 单向：主题仓库 → 站点，站点不反向合并。
- 主题已脱离最初的派生关系，没有可跟踪的其他仓库；更新只取主题仓库。
- 命令按文件合并，成功后更新 `theme.json` 里记录的主题提交。

## 更新范围

- 更新只涉及主题代码与主题资源，不涉及内容、设置与图片。
- 站点自有路径里的文件保持原样，报告里列为已跳过。
- 主题新增的默认设置不会覆盖你的设置文件。
- 主题新增的页面与组件会随更新写入；自己新增的文件不受影响。

命令会比较三个位置的文件：`theme.json` 记录的基准提交、主题最新提交与站点当前文件。只处理主题负责的文件，站点自有位置直接跳过。

## 站点自有路径

下面这些是站点自己的文件，主题更新只把它们列进报告，不修改。

| 路径 | 内容 |
|---|---|
| `content/` | 站点内容 |
| `src/data/settings/` | 五个设置文件 |
| `public/images/`、`public/author/` | 图片与头像 |
| `public/fonts/` | 字体 |
| `tools/` | 工具清单与生成记录 |
| `tests/fixtures/` | 测试快照 |
| `README.md` | 站点说明 |
| `theme.json` | 主题基准文件 |
| `.github/workflows/pages.yml` | 示例站发布配置 |

想长期保留的定制，放进这些位置或单独的文件。

## 更新前确认

- 用 git 提交或暂存当前改动；工作区不干净时命令直接拒绝执行。
- 确认能访问主题仓库，命令会拉取它的最新提交。
- 记下自己改过的主题文件，冲突时优先保留自己的改动。
- 先了解主题这一版改了什么，确认影响范围。

## 执行步骤

<details>
<summary>三条命令</summary>

```bash
npm run theme:update -- --check
npm run theme:update
npm run verify
```

</details>

- `--check` 只列清单，不写文件，先看会新增、更新、删除与冲突哪些文件。
- `theme:update` 拉取主题最新提交，按文件合并，成功后推进 `theme.json`。
- 合并是逐个文件做的，每个文件归入一类。
- 报告会分成已更新、已合并、已跳过、存在冲突、主题已删除几类。
- 没有新内容时提示已是最新，什么也不做。
- 中途失败时 `theme.json` 不更新，修正后可以重跑。
- 命令需要 git 与网络，第一次运行会拉取主题仓库。

## 冲突处理

冲突标记写进对应文件，命令以失败状态结束，`theme.json` 保持原样。

- 打开带标记的文件，保留需要的内容，删除冲突标记。
- 不要手工修改 `theme.json`，它由命令维护。
- 解决后重新执行 `npm run theme:update`；重跑前可以先再跑一次 `--check` 看剩余改动。
- 二进制文件冲突时保留站点版本，按报告核对是否需要主题的新文件。
- 报告里「主题已删除」的文件不会自动删除，确认没用之后自己删。
- 站点自有路径不会进入合并，冲突只可能出现在主题负责的文件里。
- 同一个文件反复冲突时，把自己的改动挪到单独文件或站点自有路径。

## 更新后确认

- `npm run verify` 通过，页面记录有变化时一起提交。
- 打开首页与文章页，确认样式、图片、字体与目录正常。
- 打开列表页与归档，确认筛选、分页与版本切换可用。
- 进入后台，确认主题页能正常读取和保存。
- 抽查一处自己改过的主题文件，确认定制还在。

更新结果不符合预期时，用版本控制回到更新前的提交，再重新执行更新。不要手工回滚单个主题文件，容易留下半套改动，后续更难合并。

## 示例站与字体

- 示例站同步时用 `npm run theme:update -- --include-fonts`，把主题字体一起更新。
- 再运行 `npm run font:build`，按当前内容重新生成字体分片。
- 这两个命令只服务示例站，普通站点不需要；普通站点保留自己的字体，避免字体随主题变化。

完整规则见[主题更新](https://github.com/planetarium1001/astro-versicarium/blob/main/docs/update.md)。
